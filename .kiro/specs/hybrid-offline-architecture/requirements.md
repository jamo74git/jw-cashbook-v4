# Requirements Document

## Introduction

The OAC Cashbook application is migrating from a Next.js (App Router) platform to a hybrid offline-capable architecture built on Vite + React + vite-plugin-pwa. The migration is organized around four pillars: (1) a lightweight Vite/PWA target framework, (2) a strict routing and environmental split between an offline-first field-officer capture experience and an online-only Head Office admin dashboard, (3) an offline PIN authentication mechanism that lets field officers unlock the application while disconnected, and (4) mandatory preservation of the existing domain, permission, security, and hierarchy invariants that currently depend on the Next.js server layer.

This document captures the requirements only. It deliberately surfaces the design tensions introduced by removing the Next.js server layer (middleware, header config, and `/api/*` routes) and by storing authentication material on the client. It does not prescribe an implementation; design decisions are deferred to the design phase.

The scope of this migration touches load-bearing business invariants (hierarchy shape, permission matrix, HO district segregation, time-bounded and fail-closed access, audited overrides, Turnstile, and security headers). Per project steering, these invariants MUST be carried forward unchanged.

## Glossary

- **Application**: The OAC Cashbook system as a whole after migration.
- **Vite_Bundle**: The static single-page application produced by the Vite + React + vite-plugin-pwa build.
- **PWA_Service_Worker**: The service worker generated by vite-plugin-pwa that manages asset caching and offline availability.
- **Capture_App**: The offline-first field-officer experience served under the `/capture` route layout, backed by local IndexedDB storage.
- **Admin_App**: The online-only Head Office experience served under the `/admin` route layout, reading live from Supabase.
- **Local_Store**: The client-side IndexedDB database managed via Dexie.js used by the Capture_App for local persistence.
- **Sync_Engine**: The component responsible for queueing locally captured records and reconciling them with Supabase when connectivity is available.
- **Auth_Service**: The component responsible for online authentication, offline PIN activation, offline PIN unlock, and reconnect re-validation.
- **Offline_Session**: A time-bounded authenticated state established via offline PIN unlock without a live Supabase connection.
- **PIN**: A numeric secret chosen by a Field_Officer used to unlock the Capture_App offline.
- **Cached_Credential**: The locally stored record containing a salted PIN hash, per-user salt, role metadata, and integrity protection.
- **KDF**: A key derivation function (password-hashing function) used to derive the stored PIN hash.
- **Security_Backend**: The server-side or edge component (outside the static Vite_Bundle) that performs privileged operations, Turnstile verification, and enforces the admin authorization gate. The specific host is a design decision.
- **Turnstile**: Cloudflare Turnstile bot-protection challenge and its server-side verification.
- **Field_Officer**: A user in a capture-oriented role (for example Treasurer, Chairperson, Elder, Auditor, Secretary, Overseer, Apostle) who uses the Capture_App.
- **HO_User**: A user with the HO role who uses the Admin_App.
- **Permission_Matrix**: The single source of truth mapping role + `module.function` to a permission code (V/C/E/A/S/X/M/O/R/T/-).
- **Hierarchy_Model**: The congregation hierarchy Conference > Apostolate > District > Apostleship > Overseership > Eldership > Congregation, stored in `hierarchy_levels` self-referentially via `parent_id`.
- **Access_Record**: A row in `user_hierarchy_access` defining a user's role, scope, `status`, and `[start_date, end_date]` window.
- **Access_Window**: The interval `[start_date, end_date]` during which an Access_Record is valid.
- **HO_District_Assignment**: A row in `ho_district_assignments` scoping an HO_User to specific districts.
- **Service_Status_Flow**: The directional status progression Draft → PendingAudit → AuditApproved/AuditRejected → SubmittedToOverseer → OverseerApproved/OverseerRejected → SubmittedToHO → HOReviewed.
- **Self_Review_Exception**: An audited override event logged with `action_type = SELF_REVIEW_EXCEPTION`.
- **Reconnect_Revalidation**: The mandatory re-check of a user's Access_Record and role metadata against Supabase when connectivity is restored.

## Requirements

### Requirement 1: Target Framework Migration to Vite + React + PWA

**User Story:** As a platform maintainer, I want the frontend built as a Vite + React + vite-plugin-pwa bundle, so that the Application ships as a lightweight installable offline-capable SPA instead of a Next.js server application.

#### Acceptance Criteria

1. THE Application SHALL be built and served as a static Vite_Bundle produced by Vite with React and vite-plugin-pwa.
2. THE Vite_Bundle SHALL register a PWA_Service_Worker that caches application assets required to load the Capture_App while offline.
3. WHERE the migration removes the Next.js server layer, THE Application SHALL relocate the responsibilities of `middleware.ts`, `next.config.mjs` headers, and `/api/*` routes to a Security_Backend or host-level configuration as specified in Requirements 7, 8, and 9.
4. THE Application SHALL preserve the client-facing feature behavior of the existing routes so that no in-scope user capability is removed by the framework change alone.
5. WHEN the PWA_Service_Worker serves a newer Vite_Bundle version, THE Application SHALL activate the updated bundle without discarding unsynced records held in the Local_Store.

### Requirement 2: Routing and Environmental Split

**User Story:** As a system architect, I want strict path separation between the offline-first capture experience and the online-only admin experience, so that field operation and Head Office administration have distinct data and connectivity guarantees.

#### Acceptance Criteria

1. THE Application SHALL serve the Capture_App exclusively under the `/capture` route layout.
2. THE Application SHALL serve the Admin_App exclusively under the `/admin` route layout.
3. WHILE the device is offline, THE Capture_App SHALL remain operable using data from the Local_Store.
4. WHILE the device is offline, THE Admin_App SHALL present an offline-unavailable state and SHALL NOT expose administrative data.
5. THE Admin_App SHALL read Head Office data live from Supabase rather than from the Local_Store.
6. IF a user attempts to open the `/admin` layout without the HO role, THEN THE Application SHALL deny access and route the user to the destination determined by the Permission_Matrix.
7. IF a user attempts to open a `/capture` route without a role permitted to capture, THEN THE Application SHALL deny access.

### Requirement 3: Offline-First Local Persistence

**User Story:** As a Field_Officer working with unreliable connectivity, I want my captures stored locally first, so that I can continue working without a network connection.

#### Acceptance Criteria

1. THE Capture_App SHALL persist captured records to the Local_Store using Dexie.js over IndexedDB.
2. WHEN a Field_Officer creates or edits a capture record while offline, THE Capture_App SHALL write the record to the Local_Store and mark the record as pending synchronization.
3. WHILE the device is offline, THE Capture_App SHALL read captured records from the Local_Store.
4. THE Local_Store SHALL retain pending records across Application restarts until the Sync_Engine confirms successful synchronization.
5. THE Local_Store SHALL associate every locally captured record with the authenticated user identity and role active at capture time.

### Requirement 4: Offline PIN Activation (Online First-Time Setup)

**User Story:** As a Field_Officer, I want to activate offline access once while online, so that I can later unlock the Capture_App with a PIN while disconnected.

#### Acceptance Criteria

1. WHEN a Field_Officer completes first-time activation while online, THE Auth_Service SHALL authenticate the user against Supabase before creating any Cached_Credential.
2. WHEN activation succeeds, THE Auth_Service SHALL derive a PIN hash using a KDF with a per-user salt and SHALL store the salt and derived hash in the Cached_Credential.
3. THE Auth_Service SHALL store the user's role metadata and Access_Window in the Cached_Credential at activation time.
4. THE Auth_Service SHALL apply integrity protection to the Cached_Credential so that tampering with the stored role metadata or Access_Window is detectable at unlock time.
5. THE Auth_Service SHALL NOT store the raw PIN or a reversible representation of the PIN in the Local_Store.
6. IF activation is attempted while offline, THEN THE Auth_Service SHALL reject activation and SHALL require an online connection.

### Requirement 5: Offline PIN Unlock

**User Story:** As a Field_Officer without connectivity, I want to unlock the Capture_App with my PIN, so that I can capture records offline.

#### Acceptance Criteria

1. WHEN a Field_Officer submits a PIN while offline, THE Auth_Service SHALL derive a hash of the submitted PIN using the stored per-user salt and KDF and SHALL compare it against the stored PIN hash.
2. IF the derived hash matches the stored PIN hash, THEN THE Auth_Service SHALL establish an Offline_Session scoped to the role metadata in the Cached_Credential.
3. IF the derived hash does not match the stored PIN hash, THEN THE Auth_Service SHALL reject the unlock and SHALL NOT establish an Offline_Session.
4. IF the Cached_Credential fails its integrity check, THEN THE Auth_Service SHALL reject the unlock and SHALL require online re-activation.
5. WHEN the number of consecutive failed offline PIN attempts reaches a configured maximum, THE Auth_Service SHALL lock offline unlock until an online re-authentication is performed.

### Requirement 6: Offline Session Bounds and Reconnect Re-validation

**User Story:** As a security owner, I want offline sessions to be time-limited and re-validated on reconnect, so that revoked or expired access cannot persist indefinitely on a device.

#### Acceptance Criteria

1. THE Auth_Service SHALL assign each Offline_Session a maximum offline duration (offline session TTL).
2. IF an Offline_Session exceeds its maximum offline duration without Reconnect_Revalidation, THEN THE Auth_Service SHALL end the Offline_Session and SHALL require online re-authentication.
3. WHEN connectivity is restored, THE Auth_Service SHALL perform Reconnect_Revalidation of the user's Access_Record and role metadata against Supabase.
4. IF Reconnect_Revalidation finds the Access_Record `status` is not active OR the current time is outside the Access_Window, THEN THE Auth_Service SHALL end the Offline_Session and SHALL block further capture until valid access is confirmed.
5. IF Reconnect_Revalidation finds the server-side role differs from the cached role metadata, THEN THE Auth_Service SHALL update the Cached_Credential to the server-side role and SHALL re-scope the current session accordingly.
6. THE Auth_Service SHALL treat any failure to complete Reconnect_Revalidation as a non-authorizing outcome and SHALL NOT extend the Offline_Session on such failure.

### Requirement 7: Preserved Turnstile Bot Protection Without Next.js Routes

**User Story:** As a security owner, I want Cloudflare Turnstile verification preserved after the Next.js `/api/auth/verify-turnstile` route is removed, so that login remains protected against automated abuse.

#### Acceptance Criteria

1. THE Application SHALL present a Turnstile challenge during online authentication when a Turnstile site key is configured.
2. THE Security_Backend SHALL verify the Turnstile token server-side before authentication proceeds.
3. IF the Turnstile token is missing during online authentication when a site key is configured, THEN THE Security_Backend SHALL reject the request.
4. IF Turnstile server-side verification fails, THEN THE Security_Backend SHALL reject the request and THE Application SHALL abort authentication.
5. WHERE a Turnstile secret is not configured, THE Security_Backend SHALL treat the environment as a development bypass consistent with the existing fail-open-in-development, fail-closed-in-production contract.
6. THE Security_Backend SHALL include the client remote IP derived from the forwarding headers when verifying the Turnstile token.

### Requirement 8: Preserved Security Headers Without next.config.mjs

**User Story:** As a security owner, I want the existing HTTP security headers preserved after `next.config.mjs` is removed, so that the static SPA retains equivalent transport and framing protections.

#### Acceptance Criteria

1. THE Application responses SHALL include `X-Frame-Options: SAMEORIGIN` via host-level or Security_Backend configuration.
2. THE Application responses SHALL include `X-Content-Type-Options: nosniff`.
3. THE Application responses SHALL include `Referrer-Policy: strict-origin-when-cross-origin`.
4. THE Application responses SHALL include a `Permissions-Policy` disabling camera, microphone, and geolocation.
5. THE Application responses SHALL include `Strict-Transport-Security: max-age=31536000; includeSubDomains`.
6. THE Application responses SHALL include `X-XSS-Protection: 1; mode=block`.

### Requirement 9: Preserved Privileged Admin Authorization Gate

**User Story:** As a security owner, I want the service-role admin authorization gate preserved after the Next.js `/api/admin/*` routes are removed, so that privileged writes remain HO-only and RLS-safe.

#### Acceptance Criteria

1. THE Security_Backend SHALL perform all privileged Supabase writes that previously ran in `/api/admin/*` routes and SHALL NOT expose the service-role key to the Vite_Bundle.
2. IF the service-role key is not configured, THEN THE Security_Backend SHALL reject the request with a server-configuration error.
3. IF a privileged request lacks a bearer authorization token, THEN THE Security_Backend SHALL reject the request as unauthorized.
4. WHEN a bearer token is present, THE Security_Backend SHALL resolve the user identity from the token before authorizing.
5. IF the resolved user does not have an active Access_Record with the HO role, THEN THE Security_Backend SHALL reject the request as forbidden.
6. IF a privileged request omits required body fields, THEN THE Security_Backend SHALL reject the request as invalid.
7. WHEN all authorization checks pass, THE Security_Backend SHALL perform the requested write using the service-role client.

### Requirement 10: Preserved Permission Matrix as Single Source of Truth

**User Story:** As a domain owner, I want the permission matrix to remain the single source of truth in the migrated Application, so that access decisions stay consistent and auditable.

#### Acceptance Criteria

1. THE Application SHALL derive every access decision from the Permission_Matrix rather than from inline role string comparisons in pages or components.
2. THE Permission_Matrix SHALL retain the roles HO, Apostle, Overseer, Elder, Chairperson, Treasurer, Auditor, and Secretary and the codes V, C, E, A, S, X, M, O, R, T, and `-`.
3. THE Application SHALL restrict administrative management functions to the HO role.
4. WHERE a role holds a Totals-Only (T) permission, THE Application SHALL hide line-item detail and proof images for that role.
5. WHEN an Elder or Chairperson performs an action authorized by an Override (O) permission, THE Application SHALL record a Self_Review_Exception with `action_type = SELF_REVIEW_EXCEPTION`.
6. WHILE operating in an Offline_Session, THE Capture_App SHALL enforce Permission_Matrix decisions using the role metadata in the Cached_Credential.

### Requirement 11: Preserved Hierarchy Model and Parent-Type Rules

**User Story:** As a domain owner, I want the congregation hierarchy model preserved, so that organizational structure and parent-type rules remain valid after migration.

#### Acceptance Criteria

1. THE Application SHALL preserve the Hierarchy_Model levels Conference, Apostolate, District, Apostleship, Overseership, Eldership, and Congregation stored self-referentially in `hierarchy_levels` via `parent_id`.
2. THE Application SHALL restrict user-managed hierarchy levels to District, Apostleship, and Overseership.
3. WHEN an Apostleship is created or edited, THE Application SHALL require its parent to be a District.
4. WHEN an Overseership is created or edited, THE Application SHALL require its parent to be an Apostleship.
5. IF a non-District managed level is created or edited without a parent selection, THEN THE Application SHALL reject the operation.
6. THE Application SHALL attach each Congregation to an Overseership via `overseership_id` and SHALL retain the denormalized `eldership_id`, `apostleship_id`, and `district_id` associations.

### Requirement 12: Preserved HO District Segregation and Time-Bounded, Fail-Closed Access

**User Story:** As a security owner, I want HO district segregation and time-bounded, fail-closed access preserved, so that Head Office users see only their assigned data and access is never granted on error.

#### Acceptance Criteria

1. THE Application SHALL constrain HO_User data access to the districts in the user's HO_District_Assignment records.
2. IF an HO_User has zero HO_District_Assignment records, THEN THE Application SHALL block login and SHALL NOT expose any data.
3. THE Application SHALL require an Access_Record with `status` active AND the current time within the Access_Window for authenticated access.
4. THE Application SHALL enforce the Access_Record `status` and Access_Window check in both the online authentication path and the Security_Backend authorization path.
5. IF any step of the authentication chain fails, THEN THE Application SHALL sign the user out or block access and SHALL NOT fall through to any dashboard.
6. WHILE offline, THE Capture_App SHALL enforce the cached Access_Window and SHALL treat expiry of the offline session TTL as a fail-closed block per Requirement 6.

### Requirement 13: Preserved Supabase Data Structures

**User Story:** As a data owner, I want the existing Supabase database structures preserved, so that migration does not silently alter the canonical data model or documented known issues.

#### Acceptance Criteria

1. THE Application SHALL continue to read from and write to the existing Supabase tables and views without redefining the canonical schema.
2. THE Application SHALL rely on Supabase Row Level Security for row-level filtering of segregated data.
3. WHERE a documented known issue exists in the current data model, THE Application SHALL preserve the existing behavior until a dedicated bugfix spec addresses the issue.

### Requirement 14: Offline Capture Synchronization and Reconciliation

**User Story:** As a Field_Officer, I want my offline captures synchronized and reconciled with Supabase when connectivity returns, so that no captured data is lost and status progression stays consistent.

#### Acceptance Criteria

1. WHEN connectivity is restored, THE Sync_Engine SHALL transmit pending Local_Store records to Supabase.
2. WHEN Supabase confirms a record is persisted, THE Sync_Engine SHALL mark the corresponding Local_Store record as synchronized.
3. IF a pending record fails to synchronize, THEN THE Sync_Engine SHALL retain the record as pending and SHALL retry on a subsequent synchronization.
4. WHEN synchronizing a captured record, THE Sync_Engine SHALL apply only status transitions permitted by the Service_Status_Flow.
5. IF a synchronization would violate the Service_Status_Flow direction, THEN THE Sync_Engine SHALL reject the transition and SHALL flag the record for reconciliation.
6. IF the server-side record has advanced beyond the locally captured status, THEN THE Sync_Engine SHALL apply the configured conflict-handling outcome and SHALL preserve an auditable record of the conflict.
7. THE Sync_Engine SHALL restrict correction and unlock operations to the HO role consistent with the Service_Status_Flow.

### Requirement 15: Client-Side Credential Storage Risk Controls

**User Story:** As a security owner, I want explicit controls over client-side credential storage, so that device-readable IndexedDB does not become an unmitigated authentication weakness.

#### Acceptance Criteria

1. THE Auth_Service SHALL derive the stored PIN hash using a KDF configured with work parameters intended to resist offline brute-force attack.
2. THE Auth_Service SHALL use a unique per-user salt for each Cached_Credential.
3. THE Auth_Service SHALL bind integrity protection to the Cached_Credential covering the PIN hash, salt, role metadata, and Access_Window.
4. IF the integrity protection over the Cached_Credential is invalid, THEN THE Auth_Service SHALL refuse to establish an Offline_Session.
5. WHEN a user is deactivated or their Access_Record is revoked, THE Auth_Service SHALL invalidate the Cached_Credential at the next Reconnect_Revalidation.
6. WHEN a user signs out of the Capture_App, THE Auth_Service SHALL clear the active Offline_Session state.
